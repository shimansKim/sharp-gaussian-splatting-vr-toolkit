# PC 폴더 자동 연결 안내 (Quest 3 앱 ↔ PC)

> **폐기 결정:** 웹 앱·스토어 준비물은 폐기 결정됐으며 파일은 아직 남아 있다. 새 작업 대상이 아니다.
> Quest 네이티브 뷰어는 [Splatia](../quest-native/README.md)를 본다.

> 서버는 Splatia와 공용이다. 아래 앱 조작·탐색·버튼 동기화는 웹 앱 전용이다.
> Splatia는 [PC 연결 안내](../quest-native/docs/pc-source.md)를 본다.

PC의 `outputs` 폴더(또는 원하는 폴더)에 있는 PLY·영상·사진을 Quest 앱에서 IP 주소 입력 없이 바로 열어 보는 방법이다.

## 1. PC에서 할 일

1. 저장소 폴더의 `run_quest_pc_server.bat`를 더블클릭한다.
   - 기본으로 `outputs` 폴더를 보여 준다.
   - 다른 폴더를 보려면 그 폴더를 `run_quest_pc_server.bat` 파일 위로 끌어다 놓는다. 한 번 추가한 폴더는 `quest_server_folders.txt`에 기억된다.
2. 처음 실행하면 Windows 방화벽 창이 뜬다. **개인 네트워크**를 허용한다.
3. 검은 창에 "Quest 앱에서 [PC] 탭을 누르세요"가 보이면 준비가 끝났다. 창은 열어 둔다. 닫으면 연결이 끊긴다.

> 공유한 폴더는 같은 Wi-Fi(공유기)에 있는 모든 기기가 읽기 전용으로 볼 수 있다. 집처럼 믿을 수 있는 네트워크에서만 실행한다.
> 서버는 PLY(`.ply` `.splat` `.spz`)·영상(`.mp4` `.m4v` `.webm` `.mov` `.mkv`)·사진(`.jpg` `.jpeg` `.png` `.webp` `.avif`)만 내보낸다. `.env`나 메모 같은 다른 파일, 점(`.`)으로 시작하는 숨김 파일·폴더, 폴더 밖을 가리키는 링크는 보이지도 열리지도 않는다.
> 서버는 접속 주소(Host)도 확인한다. IP 주소, `localhost`, `sharp-vr.local`, 이 PC의 이름(`PC이름`, `PC이름.local`)만 받는다. 터널 주소처럼 다른 이름으로 접속하려면 `run_quest_pc_server.bat --allow-host 터널주소`처럼 이름을 더해 실행한다.

## 2. Quest에서 할 일

1. 앱을 열고 **[PC]** 탭을 누른다.
2. 처음에는 브라우저가 "로컬 네트워크 기기 찾기" 권한을 묻는다. **허용**을 누른다.
3. **처음 한 번만 30초쯤 걸린다. 다음부터는 바로 연결된다.** 앱이 PC를 찾는 중이라는 문구와 확인 중인 주소 대역이 화면에 나오니 멈춘 것이 아니다. 기다리면 된다.
   PC 주소가 `.100`~`.199` 밖이거나 흔한 공유기 대역(`192.168.0.x`, `192.168.1.x`, `192.168.50.x`, `192.168.219.x`, `172.30.1.x`)이 아니면 몇 분 걸릴 수 있다. 그때는 기다리지 말고, 서버 창에 적힌 `PC 주소`의 숫자를 [고급: 주소 직접 입력]에 한 번만 적는다. 그러면 바로 연결되고 다음부터는 자동이다.
   연결되면 `PC 연결됨: <PC 이름>`이 보이고, 공유한 폴더의 **최근 파일**이 최신순으로 나온다(최대 1,000개). 그 위에 공유한 폴더 목록(`폴더` 표시)이 있다.
   - **파일 열기**: 행을 누르면 바로 열린다. 영상은 PC에서 받아 두지 않고 바로 재생(스트리밍)한다. 행 오른쪽에 `▶ 재생`이 보인다.
   - **폴더 탐색**: `폴더` 행을 누르면 그 안으로 들어간다. 위쪽 줄에 지금 경로가 보이고, [⬆ 상위]로 한 단계 올라가고, [최근]으로 최근 파일 목록으로 돌아온다. 1,000개보다 오래된 파일도 폴더로 들어가면 보인다.
   - **종류 거르기**: [전체] [PLY] [영상] [사진]을 누르면 그 종류만 보인다. 최근 파일 목록에서는 PC가 그 종류만 다시 모아 주므로, 최신 파일이 프레임 이미지로 가득 차 있어도 영상이 가려지지 않는다.
   - **프레임 폴더**: 렌더 프레임(PNG 수천 장)이 든 폴더는 최근 목록에 낱장으로 섞이지 않고 `프레임` 표시가 붙은 폴더 줄 하나로 나온다. 줄에는 장수와 위치가 보이고(같은 이름이 여럿이면 위치로 구분), 누르면 그 폴더 안으로 들어간다. 프레임 폴더가 둘 이상이면 「프레임 시퀀스 N곳」 한 줄로 접혀 있고, 누르면 펼쳐진다(2D 목록과 VR 패널 모두).
   - **외 N개**: 위쪽 개수 줄의 `외 N개`는 최근 목록에 다 담지 못한 파일 수다. 폴더로 들어가면 모두 보인다.
   - **더 보기**: 폴더에 파일이 아주 많아도(수천~2만 개) 화면에는 200개씩만 그린다. 목록 맨 아래의 [더 보기]를 누르면 200개씩 늘어난다. 정렬·종류를 바꾸면 다시 처음 200개부터 보인다.
   - VR 안에서 파일을 열거나 넘겨도 2D 목록은 다시 그리지 않는다. VR을 나오면 지금 보던 파일 주변 200개를 한 번만 그리고 그 위치로 스크롤한다.
   - **정렬**: 오른쪽 정렬 칸에서 최신순, 이름순(숫자 순서 인식), 크기순, 확장자순을 고른다. 고른 값은 앱이 기억한다.
   - 목록이 길어도 위쪽 거르기·정렬·경로 줄은 그대로 남고 목록만 스크롤된다.
   - VR 안 패널(B/Y로 켜고 끔)에도 같은 [종류] [정렬] [⬆ 상위] [최근] 버튼이 있다. 목록은 스틱을 위·아래로 밀거나 [▲ 위] [▼ 아래]로 넘기고, 오래 밀수록 빨라진다. 먼 곳은 [⏮ 처음] [−100] [+100] [⏭ 끝] 버튼으로 한 번에 건너뛴다. VR 패널은 보이는 줄만 그려서 파일이 몇 천 개여도 느려지지 않는다.
   - 행 오른쪽의 `기기에 저장`(PLY는 `보관`)은 오프라인용으로 파일을 앱에 복사해 두는 보조 버튼이다. 누르지 않아도 영상·사진은 바로 열린다. 2GB 이상 영상에는 이 버튼이 나오지 않는다.
4. 다음부터는 [PC] 탭을 열면 자동으로 연결한다.

앱은 다음 순서로 PC를 찾는다. IP를 입력할 일은 없다.

1. 마지막으로 성공한 주소.
2. `sharp-vr.local` 이름. Quest 브라우저는 이 이름을 풀지 못하는 경우가 있다.
3. 흔한 공유기 주소 대역(`192.168.0.x`, `192.168.1.x`, `192.168.50.x`, `192.168.219.x`, `172.30.1.x`)에서 SHARP 서버가 답하는 주소. 연결에 성공했던 대역(서버가 알려 준 PC 주소의 대역 포함)이 있으면 그 대역을 맨 앞에서 먼저 본다.
4. 3번에서 못 찾으면 [PC] 탭에 **[더 찾아보기]** 버튼이 나온다. 누르면 드문 대역(`10.0.0.x`, `192.168.43.x` 등 15개)까지 찾아본다. 이 단계는 요청이 많고 몇 분 걸리므로 자동으로 돌리지 않고 사용자가 눌렀을 때만 돌린다(회사·학교 망에서 포트 스캔으로 오인되지 않게).

한 번 찾으면 그 주소와 대역을 기억해서 다음부터는 바로 연결된다. PC의 IP가 바뀌어도 같은 대역이면 그 대역을 먼저 찾아본다.

### 대역을 찾는 방식과 시간 (개발자용)

- **어느 대역을 자동으로 훑는가.** 앱이 기억한 대역(마지막 성공·직접 입력한 주소의 대역, 최대 2개)이 있으면 그 대역만 한 바퀴 훑고 끝낸다(서버가 꺼져 있으면 Quest 실측 약 28초 뒤 실패 안내). 나머지 흔한 대역과 드문 대역은 [더 찾아보기]가 훑는다. 기억한 대역이 없는 첫 연결은 흔한 대역 5개를 모두 훑는다.
- 한 대역은 .100~.199를 먼저, 그다음 .2~.99, .200~.254, 공유기 자리 .1 순으로 본다. 대역은 하나씩 끝낸 뒤 다음 대역으로 간다. 동시 요청은 24개, 주소 하나당 0.6초까지 기다린다.
- **브라우저 소켓 풀 문제(실측).** 응답이 없는 주소로 보낸 연결 시도는 앱이 0.6초에 끊어도 브라우저의 소켓 풀에 약 20초 남는다. 풀(전체 약 256개)이 차면 살아 있는 서버로 가는 요청도 밀려 서버를 놓친다. 데스크톱 Chrome 150에서 192.168.0.x를 한 대역 훑은 직후 살아 있는 서버에 직접 요청해도 약 14초 동안 시간 초과가 났다. 그래서 시간 제한에 걸린 시도를 장부에 적고, 최근 22초 안의 개수가 150개를 넘지 않게 속도를 조절한다. 장부는 앱 전체가 공유하므로 [다시 연결]을 연달아 눌러도 풀을 비워 가며 진행한다.
- **Quest 브라우저(156) 실측(2026-11-11).** 응답 없는 사설 주소 1,500개를 동시 300개, 0.6초 제한으로 보낸 직후에도 살아 있는 서버 요청은 20ms 안팎으로 돌아왔다. 즉 Quest에서는 끊은 연결 시도가 소켓 풀에 남지 않는다. 그래도 장부 속도 조절은 그대로 둔다(데스크톱 Chrome은 필요하고, Quest 전용 분기를 두지 않는다). 서버가 꺼진 상태로 기억한 대역 없이 5개 대역을 모두 훑으면 한 바퀴에 약 5분이 걸렸다(1,270개를 150개 / 22초로 조절하는 값과 구간 4번 순회가 겹친 결과).
- 이 때문에 응답 없는 대역 하나를 끝까지 훑는 데 약 35초가 걸린다(254개 ÷ 150개 / 22초). 1단계 대역 5개를 모두 훑으면 최악 약 3분, 2단계 15개는 약 9분이다. 서버가 있는 대역에 먼저 닿으면 훨씬 짧다.
- 요청 수는 1단계 최대 약 1,270개, 2단계 최대 약 3,810개의 `GET /api/info`다. 찾으면 즉시 멈춘다.
- 서버를 찾는 기준은 `/api/info`의 `app == "sharp-quest-server"`다. 다른 기기가 8787에 답해도 오인하지 않는다.
- 접속 주소를 만드는 부분은 `scan.baseFor(host, port)`로 바꿔 끼울 수 있다(이름 기반 https 방식 대비).

연결된 뒤 [PC] 탭에 "연결 방법"이 한 줄로 나온다. "공유기 주소 자동 탐색"이면 이 기기에서는 이름(`sharp-vr.local`)이 풀리지 않는다는 뜻이다. 문제는 아니다.

## 3. 연결이 안 될 때

앱이 이유를 화면에 보여 주지만, 아래 순서로 확인하면 대부분 풀린다.

1. PC에서 `run_quest_pc_server.bat` 창이 열려 있는가.
2. Quest와 PC가 같은 Wi-Fi(같은 공유기)인가. 게스트 Wi-Fi나 "AP 격리"가 켜진 공유기는 기기끼리 보이지 않는다.
3. 방화벽에서 Python의 **개인 네트워크** 허용이 켜져 있는가.
   (설정 > 개인 정보 및 보안 > Windows 보안 > 방화벽 및 네트워크 보호 > 방화벽을 통해 앱 허용)
4. PC의 네트워크 프로필이 **개인**인가. (설정 > 네트워크 및 인터넷 > Wi-Fi 또는 이더넷 > 속성 > 네트워크 프로필 유형) "공용"이면 막힌다.
5. 서버를 켠 뒤에는 [다시 찾기]를 누른다. 서버가 꺼진 채로 시작했다면 앱은 한 바퀴만 찾아보고 실패 안내를 띄운다(자동으로 반복하지 않는다).
5-1. 로컬 네트워크 권한을 거부했다면 앱 주소창 왼쪽 자물쇠(사이트 설정)에서 허용으로 바꾼 뒤 [다시 연결]을 누른다.
6. 그래도 안 되면 [PC] 탭의 **고급: 주소 직접 입력**에 PC의 IP(예: `192.168.0.23`)를 적는다. 서버 창에 `PC 주소`로 출력된다. 한 번 적으면 다음부터는 자동으로 연결된다. 공유기 주소가 위의 흔한 대역이 아닐 때만 필요하다.

### 서버를 최신으로 바꾸기

[PC] 탭에 "PC 서버가 옛 버전입니다"가 보이거나 PC 브라우저에서 버튼 지정 페이지(`http://<PC 주소>:8787/settings/bindings`)가 열리지 않으면, 프로젝트 폴더의 서버 파일이 앱보다 오래된 것이다. 옛 서버로도 연결과 파일 열기는 되지만 버튼 지정 페이지·앱과의 버튼 배정 주고받기가 안 되고, 더 옛 서버는 목록이 덜 보이고(종류별 최근 목록·큰 폴더 나눔 없음) PC 주소를 앱이 기억하지 못한다.
프로젝트 폴더의 **`update_quest_pc_server.bat`를 더블클릭**하면 끝난다. 서버에 필요한 파일(`scripts\quest_media_server.py`, `run_quest_pc_server.bat`, 버튼 지정 페이지 `scripts\quest_bindings_page.html`·`.js`, `quest-app\src\core\bindings.js`)만 GitHub의 최신본으로 바꾸고, 다른 파일(직접 고친 대시보드 파일 등)은 건드리지 않는다. 이 파일들을 직접 고쳤다면(스테이징한 것 포함) 덮어쓰지 않고 멈춘다. 예전에 이 BAT로 받은 옛 최신본처럼 저장소에 올라간 적 있는 내용이면 직접 고친 것으로 보지 않는다. BAT 자신도 직접 고치지 않았다면 최신으로 바뀐다. 작업 폴더의 파일만 바꾸고 git 스테이징은 남기지 않는다. 끝나면 `run_quest_pc_server.bat`를 다시 실행한다(서버 창이 열려 있으면 닫고 다시).
프로젝트 폴더에 `update_quest_pc_server.bat`가 아직 없다면(이 파일이 생기기 전 버전) 명령 창(프로젝트 폴더)에서 한 번만 이렇게 실행한다.

```
git fetch origin main
git restore --source origin/main --worktree -- scripts/quest_media_server.py run_quest_pc_server.bat update_quest_pc_server.bat scripts/quest_bindings_page.html scripts/quest_bindings_page.js quest-app/src/core/bindings.js
```

`git pull`은 직접 고친 파일과 겹치면 "local changes would be overwritten"으로 막히므로 쓰지 않는다. 서버 버전은 `/api/info`의 `version`이며 최신은 3이다(3부터 버튼 지정).

## 4. 개발자 메모

- 서버: `scripts/quest_media_server.py` (읽기 전용, Range 지원, `GET /api/info|list|recent`, `GET /files/<root>/<경로>`). 테스트: `python -m unittest tests.test_quest_media_server`.
- 앱: `quest-app/src/sources/pc-connect.js`(자동 연결), `pc-source.js`(Source 계약), `proxy-url.js`와 `public/sw/source-proxy.js`(서비스 워커 프록시), `src/ui/pc-panel.js`([PC] 탭 상태 표시). 테스트: `cd quest-app && npm test`.
- 서비스 워커 연결 방법은 `public/sw/source-proxy.js` 머리 주석에 있다.
- 실측(m13, 2026-11-11, Quest 브라우저 156, ADB 원격 디버깅): 서버를 켠 상태에서 배포된 앱은 [PC]를 누르고 1초 만에 `sharp-vr.local`로 연결했다(LNA는 이미 granted). 같은 기기에서 다른 시도에는 이름이 풀리지 않고 대역 탐색으로 붙기도 했다. 그래서 이름 해석은 되다 안 되다 하는 보조 경로로 본다. 옛 서버(ae8fb7f)로도 연결과 목록 표시는 정상이었고(대역 탐색으로 20~30초), 응답하는 서버가 CORS·Host로 거절하면(허용 출처가 아닌 페이지) 요청이 18ms 만에 `TypeError`가 난다. 이는 혼합 콘텐츠 차단과 겉모습이 같으므로 안내 문구는 "차단 같다"로 고정하지 않고 서버 켜짐 확인을 먼저 권한다.
- 진단(m10): PC 쪽은 정상이었다. 서버가 `sharp-vr.local`을 광고하고(zeroconf 클라이언트로 `192.168.50.149:8787` 확인), 같은 PC에서 이름이 풀리고, Python의 인바운드 허용 규칙이 있으며, 네트워크 프로필이 개인이다. 사람이 IP를 직접 넣으면 연결된다는 것은 LNA 권한·혼합 콘텐츠 경로는 통과한다는 뜻이므로, 남는 차이는 이름 해석뿐이다. Chrome Android는 `.local` 이름을 OS 해석기에 맡기고(설계 4.2) Quest 브라우저에서 풀리지 않는 것으로 본다. 실기기 로그로 직접 확인한 것은 아니다.
- 첫 실행 직후 서비스 워커가 아직 페이지를 제어하지 않으면, 영상·사진을 PC 직접 주소(`http://IP`)로 열 때 https 페이지에서 혼합 콘텐츠로 막힐 수 있다. 그래서 `pc-source.open()`은 서비스 워커 제어를 최대 5초 기다린 뒤 같은 출처 프록시 URL로 연다.
- 실기기에서 LNA(로컬 네트워크 접근)·`sharp-vr.local`이 동작하는지는 `run_quest_pc_probe.bat`로 먼저 확인한다. 이 방식이 막히는 기기에서는 터널+페어링 코드 방식(설계 4.6)이 대안이다. 프로브 결과 전까지 구현하지 않았다.
